# 書き方のルール

このフォルダのタスクを読み書きするときのルールです。人、AI、アプリのすべてがこのルールに従います。

**AIへ：このフォルダのファイルを編集する前に、必ずこのファイルを最後まで読んでください。**

## フォルダ構成

```
tasks/
├── RULES.md          このファイル
├── TEMPLATE.md       新規チケットのテンプレート
├── NOTE_TEMPLATE.md  新規ノートのテンプレート
├── CLAUDE.md         AI向けの案内（このファイルを読むように書いてあるだけ）
├── AGENTS.md         同上
├── TAGS.md           タグの色（アプリが書く。人やAIは書き換えなくてよい）
├── templates/        選んで使うテンプレート（下の「テンプレート」を参照）
│   ├── tickets/
│   └── notes/
├── tickets/          チケット（1チケット＝1ファイル）
├── archive/          アーカイブした（片付けた）完了済みのチケット
└── notes/            ノート（議事メモ・メモ・調べたことなど。1ノート＝1ファイル）
    ├── 共通/         プロジェクトをまたぐ知識
    └── 案件A/        プロジェクトごとのフォルダ（中をさらにフォルダに分けてもよい）
```

## チケットの形

1つのチケットは、1つのmdファイルです。先頭の `---` で囲んだ部分（frontmatter）に管理用の項目を書き、その下の本文にタイトルとメモを書きます。

```markdown
---
id: 20261018-1356-k3x9
status: todo
priority: 2
start:
due: 2026-10-22
repeat:
tags: [仕事]
parent:
source:
assignee:
author:
created: 2026-10-18
done:
---

# 見積書を送る

## メモ
- 金額は前回と同じでいいか確認する
```

- タイトルは本文の先頭に `# 見出し` で書きます。
- 日付も状態も要らない小さな作業は、本文にチェックボックス（`- [ ]`）で書きます。
- 自分の期限や状態が要る作業は子チケットにして、`parent` に親のIDを書きます。

## frontmatterの項目

ここにある項目だけを、この順番で書きます。値がない項目も、行は消さずに空のまま残します。

| 項目 | 必須 | 書き方 | 意味 |
| --- | --- | --- | --- |
| `id` | 必須 | `YYYYMMDD-HHMM-xxxx` | チケットのID（下の「ID」を参照） |
| `status` | 必須 | `todo` / `doing` / `waiting` / `done` | 状態。`waiting` は返事待ち・保留 |
| `priority` | 任意 | `1` / `2` / `3` | 優先度。1が高く、3が低い。迷ったら `2` |
| `start` | 任意 | `YYYY-MM-DD` | 着手日 |
| `due` | 任意 | `YYYY-MM-DD` | 期限 |
| `repeat` | 任意 | 下の「繰り返し」を参照 | 繰り返しの規則 |
| `tags` | 任意 | `[タグ1, タグ2]` | 分類用のタグ |
| `parent` | 任意 | 親チケットのID | 親チケット。子の側にだけ書く |
| `source` | 任意 | ノートのID | このチケットを起こした元のノート。チケットの側にだけ書く |
| `assignee` | 任意 | 担当者の名前。2人以上は `[高橋, 田中]` | 担当者。1人なら名前だけ、2人以上ならリストで書く |
| `author` | 任意 | 作成者の名前 | 作成者。アプリは作るときに設定の「自分の名前」を入れる |
| `created` | 必須 | `YYYY-MM-DD` | 作成日 |
| `done` | 任意 | `YYYY-MM-DD` | 完了日 |

## ID

- 形式は `YYYYMMDD-HHMM-xxxx` です。作成した日時（現地時刻、分まで）と、英小文字と数字からなるランダムな4文字をつなげます。例：`20261018-1356-k3x9`
- チケットとノートは同じ形式のIDを使います。新しく作るときは、`tickets/`・`archive/`・`notes/` のどれにも同じIDのファイルがないことを確かめてください。

## ファイル名

- チケットは `tickets/`、ノートは `notes/` の中に、`ID.md` か `ID_好きな文字.md` の名前で置きます。例：`20261018-1356-k3x9.md`、`20261018-1356-k3x9_見積書を送る.md`
- `_` から後ろは自由に付け足し・変更して構いません。正式なタイトルは本文の見出しです。
- 新しく作るときは `ID.md` のままで構いません。アプリは起動したときに、`ID.md` のファイルに見出しを付け足すことがあります（`ID_見出し.md`）。
- ファイル名に `\ / : * ? " < > |` は使えません。タイトル部分は40文字までにします。
- ファイル名の先頭のIDと、frontmatterの `id` は必ず同じにします。

## 書き方の決まり

- 文字コードはUTF-8（BOMなし）、改行はLFです。
- 日付はすべて `YYYY-MM-DD` で書きます。
- 他のチケットやノートに触れるときは、標準の md のリンクで書きます。リンク先は、今のファイル名を相対パスで書きます（同じフォルダならファイル名だけ、違うフォルダなら `../notes/` などを付ける）。例：`[A社定例](../notes/20261015-1400-mt01_A社定例.md) の続き`
  - アプリはリンク先のファイル名の先頭の ID だけで探すので、ファイル名が変わったり `archive/` に移ったりしても開けます（ほかのエディタではたどれなくなることがあります）。
  - ID だけを文字で書いても構いません。例：`20261015-0930-p2m7 の続き`

### 正式な書き方

| 要素 | 書き方 |
| --- | --- |
| 見出し | `#` を使う（下線形式は使わない） |
| 箇条書き | `-` |
| 番号付きリスト | `1.` |
| チェックボックス | `- [ ]` と `- [x]` の2種類だけ |
| 太字 / 斜体 | `**太字**` / `*斜体*` |
| 取り消し線 | `~~取り消し線~~` |
| リンク | `[テキスト](URL または相対パス)` |
| コードブロック | バッククォート3つ |

表は次の形で書きます。列の幅は揃えません（空白や `-` を足して縦をそろえない）。区切り行は `---` で、揃えるときだけ `:---`（左）、`:---:`（中央）、`---:`（右）にします。

```markdown
| 項目 | 金額 |
| --- | ---: |
| 見積 | 1,000円 |
```

### 使わない記法

特定のツールでしか意味を持たない記法は使いません。

- `[[リンク]]`、`![[埋め込み]]`
- `> [!note]` のようなコールアウト
- `==ハイライト==`、`%%コメント%%`
- `📅 2026-10-20` のような絵文字での日付指定
- `項目:: 値` のようなDataviewの項目やクエリ
- `- [-]` や `- [/]` のような独自のチェック状態

## 繰り返し

| 書き方 | 意味 |
| --- | --- |
| `daily` | 毎日 |
| `weekdays` | 平日（月〜金） |
| `weekly:mon` | 毎週月曜（`mon` `tue` `wed` `thu` `fri` `sat` `sun`） |
| `weekly:mon,thu` | 毎週月曜と木曜（曜日は `,` でつなぎ、空白は入れない） |
| `monthly:25` | 毎月25日（その月にない日は月末） |
| `monthly:end` | 毎月末 |
| `monthly:2tue` | 毎月第2火曜（`1`〜`4` と曜日） |
| `monthly:lastfri` | 毎月最終金曜 |
| `yearly:12-25` | 毎年12月25日（`MM-DD`。`02-29` はうるう年でない年は2月28日） |
| `every:2w` | 2週ごと（`d` 日、`w` 週、`m` 月。元の予定から数える） |
| `after:7d` | 完了した日から7日後（`d` 日、`w` 週、`m` 月） |

`after:` 以外は、完了が遅れても次回の日付は変わりません。英字は小文字で書きます。

## 完了にするとき

1. `status: done` にして、`done` に今日の日付を入れます。
2. `repeat` がある場合は、次回分のチケットを新しいIDで作ります。
   - タイトル、`tags`、`priority`、`repeat`、`parent`、`assignee` を引き継ぎます。本文のメモは引き継ぎません。
   - `start` がある場合は、次回の `start` を `repeat` の規則から計算し、`due` は元の `start` から `due` までの日数を保ってずらします（例：毎月最終木曜に始めて翌日が期限の作業は、次回も最終木曜に始まる）。
   - `start` がない場合は、次回の `due` を `repeat` の規則から計算します。どちらもない場合は、完了した日から数えた日を `due` にします。
   - 次回分を作るのは、完了にした人（またはAI）だけです。
   - 完了を取り消しても、作った次回分は消しません。もう一度完了にしたときに、同じ次回分（タイトル・繰り返し・親・日付が同じ）がすでにあれば作りません。
3. 完了したチケットは削除せずに残します。片付けるときは、ファイルを `archive/` に移します（アーカイブ）。

## アーカイブと削除

- アーカイブするのは、完了したチケットだけです。子チケットがあるときは、子孫もすべて完了していれば一緒に `archive/` に移します。未完了の子孫があるうちは移しません。
- 移すときは、ファイル名も中身も変えません。親子は ID でつながっているので、`tickets/` と `archive/` に分かれても切れません。
- `archive/` のチケットも、同じ書き方のルールに従います。戻すときは `tickets/` に移します。
- 間違って作った・要らなくなったチケットは、削除して構いません。アプリは OS のごみ箱に移します（子チケットも一緒に）。完全に消すのは人が行います。

## 親子関係

- 子チケットの `parent` に親のIDを書きます。親の側には何も書きません。
- 孫やひ孫も同じ書き方です。深さに制限はありません。
- お互いを親にする（循環する）書き方はしないでください。
- 親チケットの `start` / `due` は任意です。書く場合は「親としての締切」の意味になります。

## ノート

チケットにならない情報は、ノートとして `notes/` に置きます。議事メモ、メモ、調べたこと、手順、決まっていることなど、何を書いても構いません。ID・ファイル名・タイトル（本文先頭の `# 見出し`）の決まりは、チケットと同じです。新しいノートは、`NOTE_TEMPLATE.md` か、`templates/notes/` の中の合うテンプレートをもとに作ります。

- `notes/` の下はフォルダに分けて構いません。`notes/` の直下のフォルダは、プロジェクトのまとまりです（例：`notes/案件A/`）。その中をさらにフォルダに分けても構いません。
- プロジェクトをまたぐ知識は `notes/共通/` に置きます。
- フォルダの名前を `.` で始めないでください（隠しフォルダとして読みません）。フォルダは `notes/` から9段までにしてください（それより深いノートは、アプリが読みません）。
- ノートを別のフォルダに移すと、そのノートの中のリンクと、そのノートへのリンクの相対パスがずれます。アプリはリンク先の ID で開くので開けますが、ほかのエディタでは開けなくなります。移したら、リンクの相対パスも直してください。

議事メモの例：

```markdown
---
id: 20261019-1400-m3k8
type: record
date: 2026-10-19
tags: [A社]
author:
created: 2026-10-19
---

# A社定例

## 要点

## 決定事項

## 宿題
- 見積書を送る（高橋） → [20261019-1512-x7q2](../tickets/20261019-1512-x7q2_見積書を送る.md)

## 文字起こし
（会議の文字起こしをそのまま貼る）
```

ノートの frontmatter には、次の項目だけを、この順番で書きます。値がない項目も、行は消さずに空のまま残します。

| 項目 | 必須 | 書き方 | 意味 |
| --- | --- | --- | --- |
| `id` | 必須 | `YYYYMMDD-HHMM-xxxx` | ノートのID |
| `type` | 任意 | `record` / `knowledge` / `index` | ノートの種類（下の「ノートの書き方」を参照）。記録・知識・入口。ないときは `record` とみなす |
| `date` | 任意 | `YYYY-MM-DD` | ノートの日付（会議の日、書いた日など）。「来週金曜」などを日付にするときの基準 |
| `reviewed` | 任意 | `YYYY-MM-DD` | 中身が今も正しいかを最後に確かめた日。知識のノートにだけ書く |
| `tags` | 任意 | `[タグ1, タグ2]` | 分類用のタグ |
| `author` | 任意 | 作成者の名前 | 作成者 |
| `created` | 必須 | `YYYY-MM-DD` | 作成日 |

- 見出し（要点・決定事項・宿題・文字起こし）は、議事メモ向けの目安です。要らないものは消し、議事メモでないノートでは中身に合う見出しを付けて構いません。
- 「文字起こし」の下には、原文をそのまま貼ります。整えたり要約で置き換えたりしません。起こしたタスクが正しいかを、後から確かめるためです。

## ノートの書き方

ノートには「記録」と「知識」の2つの使い方があります。1つのノートに混ぜないでください。どちらかを `type` に書きます。プロジェクトの入口になるノート（`type: index`）も置けます。

| | 記録（`record`） | 知識（`knowledge`） |
| --- | --- | --- |
| 例 | 議事メモ、作業の記録、その日に調べたメモ | 手順、仕様、今の決まり、設定の値、用語 |
| 書くこと | その時に起きたこと、話したこと | 今の正しい状態 |
| 後から | 書き換えない（誤りの訂正を除く） | 変わったら書き換える |

### 記録のノート

- `date` に、その出来事の日付を入れます。
- 後で事情が変わっても書き換えません。新しく起きたことは、新しい記録のノートに書きます。

### 知識のノート

- `reviewed` に、中身が今も正しいかを最後に確かめた日を書きます。書き換えたときと、読み直して正しいと確かめたときに更新します。
- **今の正しい状態だけを書きます。** 経緯（いつ、誰が、どう変えてきたか）、議論、見送った案は書きません。どこで決まったかを示したいときは、記録のノートへのリンクを置きます。例：`- 見積は税込で出す（[A社定例](20261019-1400-m3k8_A社定例.md) で決定）`
- 今の決まりの理由は、今も当てはまるものだけを短く書いて構いません。
- **変わったら、書き足さずに書き換えます。** 古い記述は消し、「以前は〜だったが、今は〜」とも書きません。前の版は、ファイルの版の履歴（同期サービスや Git）に残ります。
- 本文の最初に、何についてのノートかを1〜3行で書きます。
- 1つのノートには1つのテーマだけを書きます。同じテーマのノートがすでにあれば、新しく作らずにそのノートを書き換えます。
- **リンク先を読まなくても、要点が分かるように書きます。** 結論・手順・値は本文に書き、リンクは根拠や詳しい説明を見たいときのためのものにします。
- **外部の情報は写さずにリンクします。** 公式の文書などは、リンクと、使っている結論だけを書きます。写した内容は、元が変わった時点で古くなるためです。
- **長くなったら分けます。** 目安は1〜2画面です。超えたらテーマごとのノートに分け、元のノートには要約とリンクだけを残します。
- **変わりやすい情報には、確かめた日と出典を書きます。** ソフトウェアやサービスの機能・設定・料金・版などは、すぐに変わります。その記述のすぐ後に、`（2026-11-09 確認、v2.3、出典：[公式の説明](https://example.com/docs)）` のように書きます。
- 古くなったかもしれない記述に気づいたら、確かめて書き換えます。すぐに確かめられないときは、その記述の後に `（要確認：理由）` と書きます。
- 推測や確かめていないことは、確かめたことと区別できるように書きます（例：`（未確認）`）。

### 入口のノート

- プロジェクトのフォルダ（`notes/案件A/` など）の直下に1つ置き、`type: index` にします。そのプロジェクトについて調べるときは、最初にこのノートを読みます。
- 書くことは、プロジェクトの目的、今の状態、知識のノートの一覧（1つずつ、リンクと1行の要約）です。
- 知識のノートを足したり消したり、要約が変わったりしたら、一覧も直します。AI が知識のノートを書いたときは、入口の一覧も直す案を出し、人に確かめてから書き換えます。
- 記録のノートを一覧に並べる必要はありません（フォルダを見れば分かるため）。

### テンプレート

- 新しいノートは、中身に合うテンプレートをもとに作ります。`templates/notes/` に、議事メモ（記録）、手順・参照・解説（知識）、入口のテンプレートがあります。どれにも合わないメモは `NOTE_TEMPLATE.md`（記録）を使います。
- 知識のノートは、手順（やり方）・参照（仕様や設定の値）・解説（考え方や理由）を1つのノートに混ぜず、分けて書きます。
- テンプレートのファイル名（`.md` を除いたもの）が、アプリでテンプレートを選ぶときの名前になります。テンプレートは人が足したり直したりして構いません。`templates/tickets/` には、チケットのテンプレートを置けます。

## ノートからタスクを起こす

ノートからチケットを起こすときは、次の順に進めます。議事メモに限らず、メモや調べたことなど、どのノートからでも起こせます。

1. **候補を出す**：ノートを読み、タスクの候補を一覧で出します。各候補には、タイトル、担当者、期限、根拠になった箇所（議事メモなら文字起こしの発言、ほかのノートなら本文の該当する文）を付けます。担当者が2人以上なら、全員を `assignee: [高橋, 田中]` の形で書きます。
   - 「来週金曜」などの期限は、ノートの `date` を基準に `YYYY-MM-DD` にします。`date` が空なら `created` を基準にし、そのことを伝えます。
   - 期限や担当者がはっきりしないものは、空のまま候補に出します。推測で埋めません。
   - 雑談や「検討します」のような、やることが決まっていない発言は候補にしません。迷うものは、迷っていると書いて出します。
2. **人が選ぶ**：候補を出したら、どれを作るかを人に確かめます。**確かめる前にチケットを作ってはいけません。**
3. **チケットを作る**：選ばれた候補を、`TEMPLATE.md` をもとにチケットにします。ファイル名は `ID_タイトル.md` にします（宿題に書くリンクが、後で名前を変えても切れないように）。
   - `source` にノートのIDを入れます。
   - `tags` は、ノートの `tags` を引き継ぎます（人が別のタグを指定したらそれに従う）。ノートがプロジェクトのフォルダ（`notes/案件A/…`）の中にあれば、そのフォルダ名（`案件A`）もタグに足します。`notes/共通/` と `notes/` の直下のノートからのときは足しません。
   - 本文の「メモ」に、根拠になった箇所を短く書きます。
4. **ノートに書き戻す**：ノートに「宿題」の見出しがあるときだけ、その該当する行の最後に、作ったチケットへのリンク ` → [ID](../tickets/ファイル名)` を足します。リンク先の相対パスは、ノートのフォルダの深さに合わせます（`notes/案件A/` のノートなら `../../tickets/ファイル名`）。ファイル名に空白や括弧があるときは、リンク先を `<…>` で囲みます（例：`- 見積書を送る（高橋） → [20261019-1512-x7q2](../tickets/20261019-1512-x7q2_見積書を送る.md)`）。
   - 「宿題」に該当する行がなければ、「宿題」の最後に行を足します。
   - 「宿題」の見出しがないノート（知識のノートなど）には書き戻しません。チケットの `source` からノートに戻れます。
   - 書き換えるのは「宿題」だけです。ほかの部分、とくに「文字起こし」には触れません。
5. **二重に作らない**：同じノートでもう一度頼まれたときは、`tickets/` と `archive/` から `source` がそのノートのIDのチケットを先に探し、すでにあるタスクは候補から外します。

起こしたチケットとのつながりは、チケットの `source` が正です。「宿題」に書くリンクは、人が読むときにわかりやすくするためのものです（前の版の `→ ID` の書き方も、そのまま使えます）。

頼まれたら、議事メモの「要点」「決定事項」も文字起こしからまとめて書きます。

## 知識のノートを育てる

記録のノートに書いたことは、そのままでは後から探しにくく、古い話と今の話が混ざります。わかったことや決まったことは、知識のノートに取り込んで、今の正しい状態として読めるようにします。

### 記録を知識に取り込む

人に頼まれたら、記録のノート（議事メモ・作業の記録など）から、知識のノートと入口のノートを更新します。次の順に進めます。

1. **読む**：取り込む記録のノートと、そのプロジェクトの入口のノートを読みます。入口の一覧の要約から、関係しそうな知識のノートを選んで読みます。`notes/共通/` の知識のノートも、関係しそうなものは読みます。
   - 議事メモは「要点」「決定事項」を中心に読み、根拠は「文字起こし」で確かめます。
   - 知識のノートに、この記録のノートへのリンクがすでにあれば、その部分は取り込み済みです。
2. **案を出す**：知識のノートごとに、次のどれかを一覧で出します。どの案にも、根拠になった記録の箇所（議事メモなら文字起こしの発言、ほかの記録なら本文の該当する文）を付けます。
   - **書き換える**：今の記述と、新しい記述
   - **新しく作る**：使うテンプレート（手順・参照・解説）、置くフォルダ、タイトル、1〜3行の要約
   - **入口のノートを直す**：一覧に足す・消す・書き換える行と、「今の状態」が変わったときはその書き換え（今の状態には、検討中のことも書いて構いません）。プロジェクトに入口のノートがなければ、作る案
   - そのプロジェクトだけの決まりは、プロジェクトのフォルダの知識のノートに書きます。`notes/共通/` のノートには、プロジェクトをまたいで当てはまることだけを書き、プロジェクトごとの違いはそのノートへのリンクにします。
   - 知識にしないもの（その場かぎりの話、決まっていないこと、一度きりの作業）は出しません。決まったかどうか迷うものは、迷っていると書いて出します。
   - 記録が、今の知識のノートと食い違うときは、記録の `date` と知識のノートの `reviewed` を添えて、どちらが新しいかがわかるように出します。
3. **人が選ぶ**：どの案を反映するかを人に確かめます。**確かめる前に知識のノートや入口のノートを書き換えてはいけません。**
4. **書き換える**：選ばれた案を、「ノートの書き方」に従って反映します。
   - 書き足さずに書き換え、経緯は書きません。取り込んだ記述ごとに、根拠として記録のノートへのリンクを置きます（後で取り込み済みかを見分けるためにも使います）。例：`- 見積は税込で出す（[A社定例](20261019-1400-m3k8_A社定例.md) で決定）`
   - 記録の中の「来月から」「今月中」などは、記録の `date` を基準に日付（`YYYY-MM-DD` か `YYYY-MM`）にして書きます。知識のノートは後から読むので、相対的な言い方では意味が変わってしまいます。
   - 書き換えた知識のノートと、新しく作った知識のノートの `reviewed` を今日にします。
   - 記録のノートは書き換えません（取り込み済みの印も付けません）。
5. **伝える**：書き換えたノートごとに、何を変えたかを1〜2行で人に伝えます。

ノートからタスクを起こした後に、同じノートの取り込みを提案して構いません。

### 知識のノートを点検する

人に頼まれたら、知識のノートの中身を点検し、直す案を出します。直すのは、人に確かめてからです。

- 同じテーマのノートが重なっていないか（1つにまとめる案）
- ノートどうしで、記述が食い違っていないか
- 入口の一覧と、実際の知識のノートが合っているか（一覧にないノート、要約が中身と合わない行）
- `reviewed` が古いノートや、`（要確認` `（未確認）` が残っている記述（確かめて書き換える案。確かめられないものは、確かめられないと書く）
- 長すぎるノート（テーマごとに分ける案）

点検の結果は人に伝えるだけで、ファイルには書きません。アプリの「点検」の結果（切れたリンクなどの md の箇条書き）を渡されたときも、同じように直す案を出し、人に確かめてから直します。

### 知識をもとに答える

人の質問に、ノートをもとに答えるときは、次のようにします。

- そのプロジェクトの入口のノートを最初に読み、一覧の要約から読むノートを選びます。`notes/共通/` も見ます。
- 答えには、根拠にしたノートへのリンクを付けます。知識のノートにないこと（記録のノートにしかないこと、推測）は、そうとわかるように書きます。
- また聞かれそうなことや、調べてわかったことは、知識のノートに残すことを提案します。書くのは、人に確かめてからです。

## AIへのお願い

- 頼まれたチケットと項目以外は変更しないでください。関係のない行の書式を整えることもしないでください。
- 新しいチケットは `TEMPLATE.md`（頼まれたら `templates/tickets/` の中のもの）、新しいノートは `templates/notes/` の中の合うテンプレートか `NOTE_TEMPLATE.md` をもとに作ってください。プロジェクトのノートは、そのプロジェクトのフォルダに作ってください。
- ノートを書くときは「ノートの書き方」に従ってください。とくに、知識のノートには経緯を書かず、今の正しい状態だけを書いてください。新しく作る前に、同じテーマのノートがないかを探してください。
- ソフトウェアやサービスについて書くときは、覚えていることだけで書かず、公式の最新の情報を確かめてから書いてください。確かめられなかったことは、確かめていないと書いてください。
- 記録のノートから知識のノートを更新するときは、「知識のノートを育てる」の手順に従い、案を出して人に確かめてから書き換えてください。
- 知識のノートを書き換えたときは、何を変えたかを人に伝えてください。
- このルールにない項目や記法が必要になったら、使う前に人に確認してください。
