# mokkan 仕様書

## 概要と目的

標準のmdファイル群をデータベースにした、個人用のタスク管理デスクトップアプリです（Windows 用）。1つのチケットを1つのmdファイルとして持ち、人もAIもエディタもその同じファイルを直接読み書きします。

解決したい課題は4つです。

- **タスク管理ツールは操作が多い**：タスクを1つ足すのに手数がかかると、手軽に使えない。
- **AIに直接編集させたい**：MCPなどのコネクタを介さず、ファイルを読み書きするだけでAIがタスクを扱えるようにしたい。
- **独自記法は他のツールで崩れる**：ノートアプリの独自記法は、別のエディタで開くと正しく表示されない。また、mdのノートアプリの多くは、カレンダーやガントチャートで管理できない。
- **タスクとメモの距離が遠い**：タスク管理とメモを別のツールで持つと、議事メモと、そこから生まれたタスクを行き来するのに手間がかかる。議事メモ（会議の文字起こしなど）から、AIにタスクを起こしてもらいたい。

エディタの基礎部分のような車輪の再発明はせず、既製の部品を組み合わせて作ります。

## 設計原則

迷ったときは、下の5つを上から順に優先して判断します。

1. **標準mdだけを使う**：使うのはCommonMarkとGFM（GitHubの拡張記法）、それにYAMLのfrontmatterだけです。どのビューアで開いても、普通の文章として読めることを基準にします。
2. **ファイルだけがデータである**：アプリ専用のDBやキャッシュを正として扱いません。アプリを削除しても、データはそのまま使えます。
3. **編集していない部分は1文字も変えない**：開いて保存しただけでは差分を出しません。AIやGitと共存するための前提です。
4. **手軽さを優先する**：タスクの作成は1操作で済ませます。項目は必要な分だけに絞り、後から足します。
5. **ルールは明文化する**：書き方はすべてRULES.mdに書きます。人、AI、アプリが同じルールに従います。

## データ仕様

1チケット＝1ファイルです。ファイルは、管理用の項目を書くYAMLのfrontmatterと、タイトル・メモを書く本文に分かれます。

### フォルダ構成

```
tasks/
├── RULES.md        書き方のルール（人とAIの共通ルール）
├── TEMPLATE.md     新規チケットのテンプレート
├── NOTE_TEMPLATE.md  新規ノートのテンプレート
├── CLAUDE.md       Claude Code が自動で読む案内（RULES.md を読むように書くだけ）
├── AGENTS.md       ほかの多くの AI ツールが自動で読む案内（同上）
├── TAGS.md         タグの色（アプリが書く。下の「タグの色」を参照）
├── archive/        アーカイブした完了済みのチケット（ファイル名と中身は tickets/ のときのまま）
├── notes/          ノート（議事メモなど。1ノート＝1ファイル）
│   └── 20261019-1400-m3k8_A社定例.md
└── tickets/
    ├── 20261015-0930-p2m7_確定申告の準備.md   タイトルを後付けした例
    └── 20261018-1356-k3x9.md                  作った直後はこの形（次の起動で見出しが付く）
```

`notes/` は、最初のノートを作ったときにできます。

### チケットの例

```markdown
---
id: 20261018-1356-k3x9
status: todo
priority: 1
start: 2026-10-19
due: 2026-10-22
repeat:
tags: [仕事, A社]
parent: 20261015-0930-p2m7
source:
assignee: 高橋
author:
created: 2026-10-18
done:
---

# 見積書を送る

## メモ
- 金額は前回と同じでいいか確認する

## やること
- [ ] 金額を確定する
- [ ] PDFで送付する
```

- タイトルは本文先頭の `# 見出し` に書きます。frontmatterを表示しないビューアでも、何のチケットかわかるためです。
- サブタスクは2種類です。日付も状態も要らない小さな作業は、本文のGFMチェックボックスで書きます。自分の期限や状態が要る作業は子チケットにし、`parent` に親のIDを書きます。紐づけは子の側にだけ書き、親の側には書きません。書く場所が1か所なので、片方だけ更新されて食い違うことがありません。
- ファイル名は、「ファイル名」の節のルールに従います。

### frontmatterの項目

| 項目 | 必須 | 形式 | 既定値 | 用途 |
| --- | --- | --- | --- | --- |
| `id` | 必須 | `YYYYMMDD-HHMM-xxxx` | 自動で作る | チケットの識別。作り方は「ID」の節 |
| `status` | 必須 | `todo` / `doing` / `waiting` / `done` | `todo` | 状態。`waiting` は返事待ち・保留 |
| `priority` | 任意 | `1`（高）/ `2`（中）/ `3`（低） | `2` | 一覧の並び順。画面では赤・黄・灰の丸で示す |
| `start` | 任意 | `YYYY-MM-DD` | アプリで作るときは今日 | 着手日。ガントチャートの棒の始点 |
| `due` | 任意 | `YYYY-MM-DD` | 空 | 期限。カレンダーとガントチャートの終点 |
| `repeat` | 任意 | 「書き方のルール」の書式 | 空 | 繰り返しの規則 |
| `tags` | 任意 | 文字列のリスト | `[]` | 絞り込み（プロジェクト、分類など） |
| `parent` | 任意 | 親チケットの `id` | 空 | 親チケットへの紐づけ。子の側にだけ書く |
| `source` | 任意 | ノートの `id` | 空 | このチケットを起こした元のノート（議事メモなど）。チケットの側にだけ書く。この行がない古いチケットは空として扱う |
| `assignee` | 任意 | 担当者の名前。2人以上は `[高橋, 田中]` | アプリで作るときは設定の「自分の名前」 | 担当者。1人なら文字列、2人以上ならリストで書く。アプリの中では名前の配列として扱い、書き出すときに人数で形を選ぶ。開いて保存しただけでは書き換えない |
| `author` | 任意 | 作成者の名前 | 設定の「自分の名前」 | 誰が作ったか。アプリは作るときに個人設定の名前を入れる（未設定なら空）。この行がない古いチケットは空として扱う |
| `created` | 必須 | `YYYY-MM-DD` | 作成日 | 作成日。自動で入る |
| `done` | 任意 | `YYYY-MM-DD` | 空 | 完了日。完了時に自動で入る |

この表にない項目は、使いながら必要になったら足します。見積時間、依存関係、時刻は、初版では持ちません。

更新日時は項目として持たず、ファイルの更新日時を表示と並べ替えに使います。人やAIが編集したときにも自動で変わるためです。ただし同期サービスが書き換えただけで変わることもあるので、「内容を編集した日時」とずれる場合があります。

### 親子関係のルール

- 階層の深さは制限しません。孫やひ孫も、同じ `parent` の書き方で表します。
- 循環（AとBが互いを親にしている状態など）は禁止です。アプリが検出したら警告を出します。
- `parent` の親が存在しない子は、一番上の階層に表示して警告を付けます。
- 親チケットの `start` / `due` は任意です。書いていない場合は、子孫全体の期間を表示に使います。書いてある場合は「親としての締切」として扱い、子孫がはみ出したら警告を出します。

### ノート

チケットにならない情報（議事メモ、調べたこと、決めたことなど）は、ノートとして `notes/` に置きます。タスクとメモを同じフォルダ・同じアプリで持ち、行き来の手間をなくすためです。

- 1ノート＝1ファイルです。ID・ファイル名・タイトル（本文先頭の `# 見出し`）の決まりは、チケットと同じです。IDは、チケット（`tickets/`・`archive/`）とノートをまたいで重ならないようにします。
- frontmatter はチケットより少なくします。状態や期限は持ちません。
- プロジェクトなどのまとまりは、タグで表します。起こしたチケットには、ノートのタグを引き継ぎます。

| 項目 | 必須 | 形式 | 既定値 | 用途 |
| --- | --- | --- | --- | --- |
| `id` | 必須 | `YYYYMMDD-HHMM-xxxx` | 自動で作る | ノートの識別 |
| `date` | 任意 | `YYYY-MM-DD` | 作成日 | 会議などの日。一覧の並び順と、「来週金曜」などを日付にするときの基準 |
| `tags` | 任意 | 文字列のリスト | `[]` | 絞り込み（プロジェクトなど） |
| `author` | 任意 | 作成者の名前 | 設定の「自分の名前」 | 誰が作ったか |
| `created` | 必須 | `YYYY-MM-DD` | 作成日 | 作成日 |

議事メモは、次の形を基本にします（NOTE_TEMPLATE.md）。見出しは目安で、要らないものは消して構いません。

```markdown
---
id: 20261019-1400-m3k8
date: 2026-10-19
tags: [A社]
author:
created: 2026-10-19
---

# A社定例

## 要点

## 決定事項

## 宿題
- 見積書を送る（高橋） → [20261019-1512-x7q2](../tickets/20261019-1512-x7q2_見積書を送る.md)

## 文字起こし
（会議の文字起こしをそのまま貼る）
```

- 会議ツールの文字起こしは、md 以外の形式やクラウドの上にしかない文書として保存されることが多く、そのままではAIもアプリも読めません。本文を「文字起こし」の見出しの下に貼ります。原文を残しておくと、起こしたタスクが正しいかを後から確かめられます。
- 起こしたチケットとのつながりは、チケットの `source` が正です。ノートの「宿題」に書くチケットへのリンクは、アプリの外（ほかのエディタや GitHub など）で見たときにわかりやすくするための書き戻しです。両者が食い違っても、アプリは `source` を使います。

### 議事メモからタスクを起こす

AI（Claude Code などの AI ツール）に、議事メモからタスクを起こしてもらうときの手順です。RULES.md にも同じ手順を書き、どのAIも同じように動くようにします。

1. **候補を出す**：AIはノートを読み、タスクの候補を一覧で出します。各候補には、タイトル、担当者、期限、根拠になった発言（文字起こしの該当箇所）を付けます。期限の「来週金曜」などは、ノートの `date` を基準に日付にします。
2. **人が選ぶ**：人が、作る候補を選び、必要なら直します。文字起こしは雑談や「検討します」も拾いやすいので、確認せずに作ることはしません。
3. **チケットを作る**：選ばれた候補を、TEMPLATE.md をもとにチケットにします。`source` にノートのIDを入れ、ノートの `tags` を引き継ぎます。
4. **ノートに書き戻す**：ノートの「宿題」の該当する行の最後に、作ったチケットへの md のリンクを書きます。リンクが後で切れないよう、チケットのファイル名は初めから `ID_タイトル.md` にします。前の版の ` → ID` の書き方もそのまま読めます（例：`- 見積書を送る（高橋） → [20261019-1512-x7q2](../tickets/20261019-1512-x7q2_見積書を送る.md)`）。該当する行がなければ行を足し、「宿題」の見出しがなければ「文字起こし」の前（なければ本文の最後）に見出しごと足します。書き換えるのは「宿題」だけで、ほかの部分、とくに「文字起こし」には触れません。
5. **二重に作らない**：同じノートでもう一度頼まれたときは、`source` がそのノートのチケットを先に確かめ、すでにあるものは作りません。

あわせて、頼まれれば「要点」「決定事項」もAIがまとめます。

AIがこの手順に気づけるよう、`tasks/` に `CLAUDE.md`（Claude Code が自動で読む）と `AGENTS.md`（ほかの多くの AI ツールが自動で読む）を置き、「先に RULES.md を読む」とだけ書きます。2つは同じ中身で、原本は `templates/AI_GUIDE.md` の1つです（原本を `templates/CLAUDE.md` という名前にすると、このリポジトリを開発する Claude Code にも読み込まれてしまうため）。

### ID

IDは、作成した日時とランダムな4文字をつなげた `YYYYMMDD-HHMM-xxxx` です（例：`20261018-1356-k3x9`）。番号を管理する仕組みが要らず、複数人で同時に作っても重なりません。

- 日時は分までです。それだけだと、2人が同じ分に作ったときにIDが重なります。
- そこで、英小文字と数字からなるランダムな4文字を足します。同じ分に作っても、重なる確率は約170万分の1です。
- ファイルは、同じ名前のファイルがない場合だけ作る方法で書き込みます。万一重なったら、ランダムな部分を作り直します。
- 時刻は、作った人のPCの現地時刻を使います。
- AIがチケットを作るときも同じ形式で作り、既存のファイルと重ならないことを確かめます。

### ファイル名

ファイル名は「ID」か「ID＿好きな文字」です。アプリは先頭のIDだけを読み、それより後ろは無視します。そのため、作った後でタイトルを付け足しても、付け替えても問題ありません。

- **形式**：`20261018-1356-k3x9.md` または `20261018-1356-k3x9_見積書を送る.md` です。IDの中で `-` を使っているので、区切りは `_` にして紛らわしさをなくします。
- **正式なタイトルは本文の見出し**：ファイル名のタイトル部分は、エクスプローラーで見分けるための飾りです。本文の `# 見出し` と食い違っていても構いません。
- **アプリは起動時に、ID だけのファイルにだけ見出しを付ける。それ以外は自動で名前を変えない**：「新規」で作ったチケットは `ID.md` のままなので、エクスプローラーなどで見分けられるよう、起動して読み込んだ後に1回だけ `ID_見出し.md` にします。同期フォルダで名前の変更が重なると競合の原因になるため、次のように限ります。
  - 対象は `tickets/` と `notes/` の、名前が ID だけのファイル。`archive/` は移したときの名前のまま。すでにタイトルがある名前や手で付けた名前は変えず、後から見出しを変えても付け替えない。
  - 見出しが空のファイル、frontmatter が読めない・id がファイル名と違うファイルは変えない。
  - 作成者（`author`）が自分か空のファイルだけ（他の人が作ったファイルには触れない）。
  - 変える先に同じ名前のファイルがあれば変えない。
  - 起動したときと、フォルダを選び直したり準備したりして開き直したときに1回だけ行う。起動中に作ったチケットにはかからない（次の起動で付く）。名前を変えたら、起動後に「◯件のファイル名に見出しを付けました」と案内する。
  - 2台の PC でほぼ同時に起動すると、同じファイルを両方で変えようとして、同期サービスが競合コピーを作ることがある。そのときは今の警告（同じ `id` のファイルが複数ある）で気付ける。
  エクスプローラーで手で変えても構いません。
- **使えない文字と長さ**：Windowsでファイル名に使えない `\ / : * ? " < > |` は、アプリが名前を付けるときに取り除きます。同期フォルダの深い階層でもパスが長くなりすぎないよう、タイトル部分は40文字までにします。
- **チケット同士はIDでつなぐ**：`parent` はIDで書くので、名前を変えても切れません。本文で他のチケットやノートに触れるときは、標準の md のリンク（`[タイトル](../notes/ID_….md)`）で書きます。ほかのエディタや GitHub でもたどれるよう今のファイル名で書きますが、アプリはリンク先のファイル名の先頭の ID だけで探すので、名前を変えたり `archive/` に移したりしても開けます。ID だけを文字で書いても構いません。アプリは本文中のIDとリンクを見つけて、Ctrl+クリックで開けるようにします。
- **ファイル名とfrontmatterのIDは一致させる**：frontmatterの `id` も残します。ファイルを手で複製した場合や競合コピーを見つけるのに使うためです。両者が食い違う場合は警告を出します。

### 複数人で使うときの備え

主に個人で使うことを想定していますが、複数人で同じフォルダを使っても困らないよう、次のルールを入れています。

- **担当者の項目**：`assignee` を先に用意しておきます。後から全チケットを書き換える必要がなくなります。
- **繰り返しの次回分**：完了の操作をした人（アプリまたはAI）だけが作ります。フォルダを監視して自動で作る方式にすると、各自のアプリが同じ次回分を重ねて作ってしまうためです。
- **自動削除の範囲**：自動で削除するのは、自分のアプリが作ったばかりの空のチケットだけです。他の人が作ったファイルには触れません。人が明示的に削除するときは、OS のごみ箱に移します（完全には消しません）。
- **他の人のファイルの名前は変えない**：起動時に見出しを付け足すのは、作成者が自分か空のファイルだけです（「ファイル名」の節）。
- **個人の設定は分ける**：表示の好みなどの個人設定は `tasks/` の外に置き、共有するデータと混ぜません。共有したい設定（タグの色）は `tasks/TAGS.md` に置きます。

### 同期フォルダで共有するときの対策

複数の PC や複数の人で使うときは、Google Drive・OneDrive・Dropbox などの同期フォルダを使います。同期サービスは、同じファイルが複数の場所でほぼ同時に変わると、両方を残すために競合コピーを作ります。ただし、そのことを知らせてくれるとは限りません。そこで、アプリの側で競合を見つけます。

- **競合コピーの検出**：`tickets/` の中に、ファイル名がIDで始まらないmdファイルや、同じ `id` を持つファイルが2つ以上あれば、競合コピーとみなして警告します。競合コピーの名前の付け方はサービスやバージョンによって変わるため、名前ではなく「IDとの食い違い」で判定します。
- **競合の解消**：警告から2つのファイルの差分を並べて表示し、どちらを残すかを選べるようにします。両方の変更を残したい場合は、手でまとめます。
- **ファイルをPCにも置く**：同期サービスの多くには、ファイルをクラウドにだけ置き、開くときに取ってくる設定（オンデマンド・ストリーミングなど）があります。ファイル監視やAIによる直接編集を確実に動かすため、`tasks/` はPCにも実体を置く設定（ミラー・常にこのデバイスに保持など）にします。
- **関係のないファイルは無視する**：同期のための一時ファイルや隠しファイルなど、md以外のファイルは読み込みません。
- **同期の遅れを前提にする**：他の人の変更は、数秒から数分遅れて届きます。届いた変更は、ファイル監視が拾って反映します。
- **同期フォルダの中でGitは使わない**：同期フォルダの中にGitの管理用フォルダを置くと、同期の途中で壊れることがあります。変更の履歴は、同期サービスの版の履歴でたどります。

### タグの色

タグの色は、`tasks/TAGS.md` の frontmatter に「タグ: 色相（0〜359）」で書きます。同期フォルダで別の PC とも共有するため、個人設定ではなく `tasks/` に置きます。アプリは md 以外のファイルを無視する決まりなので、md のファイルにしています。

```markdown
---
colors:
  仕事: 210
  家: 30
---

# タグの色

mokkan がタグの色（色相、0〜359）を書き込むファイルです。
```

- 保存するのは色相だけです。鮮やかさと明るさは画面が一定にし、淡い色（パステル調）で表示します（「色の意味」を参照）。
- 色を選んでいないタグは書きません。タグの名前から色相を決めるので、同じタグはどの PC でも同じ色になります。
- 書き換えるのは、変えたタグの行だけです（`setFields` と同じ考え方）。選んだその場でファイルを読んでから1行を書き換えるので、外部の変更を上書きしません。ファイルがなければ作ります。
- `TAGS.md` も監視し、別の PC で変わったら反映します。同期サービスの競合コピー（`TAGS (1).md` など）や読めない `TAGS.md` は、警告に出します。
- 利用者のデータなので、ルールのファイル（設定の「原本にする」の対象）には入れません。AI は書き換えなくて構いません。

## 書き方のルール（RULES.md）

RULES.mdは、人、AI、アプリが共通で従う唯一の書き方の基準です。AIには、編集の前に必ずこのファイルを読ませます。内容は `templates/RULES.md` を参照してください。

要点は次のとおりです。

- 文字コードはUTF-8（BOMなし）、改行はLF、日付は `YYYY-MM-DD`。
- エディタの出力と同じ「正式な書き方」に揃える（見出しは `#`、箇条書きは `-`、チェックボックスは `- [ ]` / `- [x]` のみ、など）。
- 特定のツールの独自記法（`[[リンク]]`、コールアウト、`==ハイライト==`、絵文字の日付、Dataview、独自のチェック状態）は使わない。
- 繰り返しの書式は `daily` / `weekdays` / `weekly:mon,thu` / `monthly:25` / `monthly:end` / `monthly:2tue` / `monthly:lastfri` / `yearly:12-25` / `every:2w` / `after:7d`。
- 完了時は `status: done` と `done` を入れ、`repeat` があれば新しいIDで次回分を作る。完了したチケットは削除せず、片付けるときは `archive/` に移す（アーカイブ）。
- 他のチケットやノートには、標準の md のリンク（`[タイトル](../notes/ID_….md)`）で触れる。ID だけを文字で書いてもよい。
- 議事メモからタスクを起こす手順（候補を出す→人が選ぶ→作る→「宿題」に `→ [ID](…)` を書き戻す）。

## アプリ構成

ElectronとTypeScriptで作るデスクトップアプリです。データは `tasks/` フォルダのmdファイルだけで、アプリ、AI、他のエディタがそれぞれ直接読み書きします。

```
┌─ Electronアプリ（TypeScript）─────────────────┐     外部からの編集
│ ┌─ 画面（レンダラープロセス）─────────────┐ │   ┌──────────────────┐
│ │  一覧・ノート  編集画面  検索           │ │   │ AI               │
│ │  カレンダー    ガントチャート           │ │   │ RULES.mdを読んで │
│ └─────────────────────────────────────────┘ │   │ ファイルを直接編集│
│ ┌─ 裏方（メインプロセス）─────────────────┐ │   └────────┬─────────┘
│ │  ファイル読み書き  ファイル監視         │ │   ┌────────┴─────────┐
│ │  チケット作成                           │ │   │ 他のエディタ     │
│ └─────────────────────────────────────────┘ │   └────────┬─────────┘
└──────────────────────┬────────────────────────┘            │
                       │ 読み書き・監視                      │ 直接読み書き
┌──────────────────────┴────────────────────────────────────┴─────────┐
│ tasks/ フォルダ（唯一のデータ）  RULES.md・tickets/・notes/・TAGS.md │
└──────────────────────────────────────────────────────────────────────┘
```

アプリは画面と裏方に分かれ、ファイルに触るのは裏方だけです。AIや他のエディタが書き換えた内容は、裏方のファイル監視が拾って画面に反映します。

### 使う部品

| 役割 | 部品 | 選んだ理由 |
| --- | --- | --- |
| デスクトップアプリ | Electron | 全部TypeScriptで書け、情報が多い |
| 画面のフレームワーク | React | SVAR GanttのReact版に合わせる。Milkdownとも組み合わせられる |
| 本文エディタ | Milkdown | md前提の設計で、書き出し方を設定で固定できる |
| frontmatterの読み書き | yaml | コメントや書式を保ったまま書き換えられる |
| カレンダー | FullCalendar 7 | 月表示などの標準機能はMITライセンスで使える |
| ガントチャート | SVAR Gantt | MITライセンス版に、サブタスクの階層表示、まとめタスク、棒のドラッグが含まれる。日付のないタスク、グループ化、まとめタスクの期間の自動計算は有料のPRO版の機能なので、アプリ側で補う |
| ファイル監視 | chokidar | Node.jsで定番の監視ライブラリ |
| AI でタスクを起こす | Claude Code（`claude -p`） | パソコンに入っている Claude Code を呼ぶので、APIキーの管理が要らない。アプリには同梱しない |

Frappe Ganttは階層のない平らなタスクしか扱えないため、候補から外しました。（[SVAR Gantt](https://docs.svar.dev/react/gantt/overview)、[Frappe Gantt](https://github.com/frappe/gantt)）

## 機能仕様

アプリの機能は9つです。どの機能も、書き込むのは対象チケット・ノートの必要な部分だけです。画面の色の決まりは、次の「色の意味」の節にまとめています。

### 1. 新規作成（1ボタン）

- ボタンかショートカットキー1つで、TEMPLATE.mdから新しいチケットを作ります。
- `id`、`created`、`status: todo`、`priority: 2` と、着手日（`start`）に今日を自動で入れます。設定の「自分の名前」があれば、作成者（`author`）と担当者（`assignee`）にも入れます。絞り込みでタグを1つだけ選んでいるときは、そのタグも付けます。タイトル行にカーソルを置いた状態で開きます。
- 期限（`due`）は空のままにします。今日を入れると、変え忘れたときに翌日「期限切れ」になるためです。
- 初めの値はアプリで作るときだけ入れます。`TEMPLATE.md` と、AI や手で作るときの決まりは変えません。ノートの「＋ ここからチケット」でも、同じ初めの値を入れます。
- タイトルも本文も空のまま閉じた場合は、ファイルを削除します。空のチケットがたまるのを防ぐためです。初めの値が入っていても、項目を変えていなければ削除します。
- 作った直後のファイル名は `ID.md` です。次に起動したときに、見出しを付け足します（「ファイル名」の節）。

### 2. 一覧

- 未完了のチケットを、期限の近い順に並べます。期限が同じ場合は、優先度の高い順にします。
- 並び順は、期限・着手日・優先度・作成日・更新日時・状態・タイトルから選び、向き（昇順・降順）も切り替えられます。値のないチケットは、向きに関係なく最後に置きます。選んだ並び順は個人設定（`tasks/` の外）に保存し、次に起動したときも使います。
- 各行に、優先度の丸（高・中・低を赤・黄・灰）、状態、タグの札（タグの色）、親チケット、担当者（複数人なら並べる）、期限と着手日を出します。
- 状態、タグ、優先度、担当者で絞り込めます。担当者は「自分」（設定の名前）と「未割り当て」も選べます。担当者は「選んだ人のどれかが担当に入っている」で絞り、「未割り当て」は担当者が空のものです。この絞り込みは、カレンダーとガントチャートでも共通です。
- `start` が未来の日付のチケットは、既定では隠します。
- 完了したチケットは既定では隠し、「完了も表示」で並べられます。
- アーカイブ（`archive/`）したチケットは既定では隠し、「アーカイブも表示」で並べられます。この絞り込みは、カレンダーとガントチャートでも共通です。
- 一覧の下の「まとめてアーカイブ」で、完了してから指定した日数（既定30日）たったチケットを、件数を確かめてからまとめて `archive/` に移せます。自動では移しません。
- 一覧の上に、確認が必要なファイルを警告として出します。対象は、競合コピー（ファイル名がIDで始まらない、同じ `id` が複数ある）、ファイル名と `id` の食い違い、frontmatterが読めない、親が見つからない、親子の循環、`start` が `due` より後、`source` のノートが見つからない、`TAGS.md` が読めない・競合コピーがある、です。ファイルは自動では直しません。

### 3. 編集画面

チケットとノートの両方を、同じ編集画面で開きます（ノートのプロパティは「8. ノート」を参照）。

- 画面上部に、frontmatterを編集するプロパティフォームを置きます（状態、優先度、日付、繰り返し、担当者、作成者、タグ、親チケット、元のノート）。フォームで値を変えると、frontmatterの該当する行だけを書き換えます。
  - 担当者・作成者・タグは、これまでに入力した値を候補に出します。担当者はタグと同じ入力欄で、複数人を入れられます（半角の「,」で区切るので、名前に「,」は使えません）。
  - タグの色は、タグの欄のチップの左の色の印を押して選びます。色見本（12色）と色相の帯があり、「自動の色に戻す」で名前から決める色に戻せます（保存先は「タグの色」の節）。
  - 親チケットを開くと、その子チケットの一覧も表示します。「元のノート」は親チケットと同じ選択欄で、選び直し・外すこともでき、「開く」でノートを開きます。
  - 繰り返しは、種類（毎日・平日・毎週・毎月・毎年・◯日ごと・完了から◯日後など）を選ぶと必要な項目だけが出るフォームで指定します。選んだ内容は「毎月第2火曜」のように日本語で表示します。書式（RULES.md の書き方）を直接書く欄も残しますが（AIや手で書いた値を壊さないため）、普段は隠し、「書式で書く」を押したときと、プルダウンで表せない値のときだけ出します。
- 繰り返し（`repeat`）のあるチケットを完了にすると、保存してから次回分のチケットを作り、開くための案内を出します。作り方は RULES.md の「完了にするとき」のとおりです。完了を取り消しても次回分は消さず、もう一度完了にしても同じ次回分がすでにあれば作りません。
- 画面下部は、本文を編集するWYSIWYGエディタです（保存の仕組みは「エディタ設計」の節）。保存は入力が止まってから自動で行います。
- 本文の上のツールバーで、記法を打たずに書式を付け外しできます。標準の md で書けるものだけを置きます。
  - 元に戻す・やり直す、段落の種類（本文・見出し2〜4。見出し1は本文の先頭のタイトル用なので選べないが、本文の途中にあれば「見出し1」と出す）
  - 太字・斜体・取り消し線・インラインコード
  - 箇条書き・番号付きリスト・チェックボックス・字下げ・字下げを戻す
  - 引用・コードブロック・区切り線・リンク（小さな欄に URL を入れる。文字を選んでいればその文字に付け、空にすると外す。外部のブラウザで開くのは http/https だけ）
  - 表：3行×3列で挿入し、表の中では行・列の追加と削除ができます（セル間は Tab で移動）。列の幅を揃えずに書き出し、セルを1つ変えるとその表全体が正式な書き方で書き出されます。カーソルのあるセルを色付けし、その行と列も薄く色付けします（画面だけの飾り）。
  - ボタンはカーソル位置の書式に合わせて押された状態で表示し、まとまりごとに区切って、狭い幅ではまとまりの単位で折り返します。
- 本文で `[[` と打つと（日本語入力のままの `「「` でもよい）、チケット・ノート・アーカイブの候補を出します。タイトルか ID の部分一致で絞り込み、最近更新したものを上にします。↑↓で選んで Enter（または Tab・クリック）で、打った `[[…` を `[タイトル](相対パス)` の標準の md のリンクに置き換えます。`[[` はファイルに残しません。Esc で閉じます。
- 本文の中のチケットやノートのIDと、他のチケット・ノートへの md のリンクには印を付け、Ctrl+クリックで開けるようにします（ふつうのクリックはカーソルを置くだけ）。リンクはリンク先のファイル名の先頭の ID で探すので、名前が変わっても開けます。ID の横には、タイトルを薄く表示します。印とタイトルは画面だけの飾りで、本文には書きません。コードの中のIDには付けません。
- 編集画面の上に「← 戻る」を出し、直前に開いていたノートやチケットに戻れるようにします。Alt+← とマウスの「戻る」ボタンでも戻ります。
- 編集画面の上部から、アーカイブ（完了したチケットだけ。未完了の子孫があるときは移さない。子孫も一緒に移す）、アーカイブから戻す、削除（確認してから、子孫と一緒に OS のごみ箱に移す）ができます。

### 4. カレンダー

- 月単位で表示します。`due` の日にチケットを置き、`start` があれば `start` から `due` までの帯で表示します。
- 予定の塗り方は状態、左端の線は最初のタグの色、「高」の優先度には赤い丸、期限切れには赤い枠と「!」を付けます（「色の意味」を参照）。タグのないチケットには線を付けません。
- 予定にマウスを乗せると、ガントチャートと同じ「親 > 子 > 孫」の経路を表示します。子チケットの予定は、名前の前にすぐ上の親のタイトルを小さく付けます（「親 › 子」）。
- 同じ日に並ぶ予定は、親子のまとまりの中では親→子→孫の順に上から並べます。まとまりどうしは FullCalendar の既定の順（始まりが早い→期間が長い→タイトル）で、まとまりの中で一番上に来る予定の位置にまとまり全体を置きます。複数日の帯は FullCalendar が段を詰めて並べるため、日によっては子が上に来ることがあります。
- 見出しの真ん中の「?」を押すと、凡例を出します。
- クリックすると、そのチケットの編集画面を開きます。
- ドラッグで日付を動かす機能は、今後検討します（「今後の候補」を参照）。

### 5. ガントチャート

- `start` から `due` までを棒で表示します。`start` がないチケットは、`due` の日に印だけを表示します。
- タグごと、または親チケットごとに行をまとめて表示できます。
- 棒の塗り方は状態で、カレンダーと同じです（「色の意味」を参照）。期限切れの行は棒を赤い枠で囲み、名前の横に「!」を付けます。名前の横には優先度の丸を出し、名前の列の左端にはタグの色の線を付けます（タグごとにまとめたときは、見出しの棒をタグの色にする）。
- 完了した行は、名前の列も棒と同じく灰色＋取り消し線にします。
- ツールバーの右の「?」を押すと、凡例を出します。

親子関係が何段になっても崩れないように、次のルールで表示します。

1. 行は「親→子→孫」の順に並べ、名前の欄で字下げします。字下げは4段で止めます。それより深い階層は、マウスを乗せると「親 > 子 > 孫」の経路を表示します。
2. 親ごとに折りたためます。最初は2段目まで開いた状態で表示します。
3. 親の棒は、子孫全体の期間を示す「まとめ棒」として、両端を下に尖らせた形で描きます。塗りは親自身の状態です（子がすべて完了しても、親が未完了なら灰色にしない）。
4. 親の `due` を子孫がはみ出している場合は、警告の印を付けます。
5. 絞り込んだときは、条件に合う子孫の祖先も薄く表示して、何の作業かわかるようにします（完了の灰色＋取り消し線とは、取り消し線の有無で見分ける）。
6. 日付のないチケットは、行だけ表示して棒は描きません。

### 6. 検索

- 画面の上に検索欄を置き、どの画面からでも使えます。Ctrl+K で検索欄に入ります。
- チケット・ノート・アーカイブをまとめて、タイトルと本文から探します（frontmatter は探しません）。結果は「種類（チケット／ノート／アーカイブ）・タイトル・当たった箇所の前後の文」を並べ、タイトルに当たったものを上に、同じなら最近更新したものを上にします（50件まで）。
- 部分一致で、ひらがなとカタカナ、全角と半角、大文字と小文字を区別しません。空白（全角も）で区切った複数の語は「すべて含む」で探します。
- ノートの「文字起こし」は、当たりが増えすぎるので既定では探しません。「ノートの文字起こしも探す」を付けたときだけ探します。
- 結果をクリック（または↑↓と Enter）すると、そのファイルを開き（「← 戻る」で戻れる）、本文の中で当たった箇所を選んで見えるところまで動かします。
- 今の絞り込み（タグなど）は、検索の結果には効かせません。
- 本文は持ち続けず、探すたびに裏方がファイルを読みます（ファイルだけがデータ）。件数が増えて遅くなったら、裏方で本文を持つ方法に切り替えます。

### 7. 外部からの変更への追従

- `tickets/`・`archive/`・`notes/` と `TAGS.md` を監視し、AIや他のエディタ、同期サービスでファイルが変わったら、一覧・カレンダー・ガントチャート・ノートにすぐ反映します。
- 開いているチケットやノートが未編集なら、自動で読み直します。
- 編集中に外から変更された場合は、上書きせずに通知し、自分の変更を残すか、外部の変更を読み込むかを選ばせます。

### 8. ノート

- 画面上部の切り替えに「ノート」を置きます（一覧／カレンダー／ガント／ノート）。ノートの一覧は、`date` の新しい順に並べ、各行に「このノートから作ったチケット ◯件中◯件完了」を出します。タグの絞り込みは一覧・カレンダー・ガントと共通で、ノートのタグも選べます。
- ノートの作成は、ノートの画面の「＋ 新規ノート」（Ctrl+N）で行います。NOTE_TEMPLATE.md から作り、`date` には今日を入れます。空のまま閉じたら削除するのは、チケットと同じです。
- ノートの編集画面は、チケットの編集画面を使い回します。プロパティは `date`・`tags`・`author` だけです。本文の保存の仕組み（編集していないブロックを元に戻す、外部の変更との競合の確認）も同じです。
- ノートの編集画面の下に、「このノートから作ったチケット」（`source` がこのノートのチケット）を、状態付きで並べます。クリックでそのチケットを開きます。
- 「＋ ここからチケット」で、AIを使わずに手でチケットを起こせます。押すと小さな入力欄でタイトルを聞き、`source` にノートのIDを入れ、ノートのタグを引き継いだチケットを作ります（ファイル名は `ID_タイトル.md`）。作ったチケットを開きます。
  - 「宿題」の箇条書きの項目にカーソルを置いて押したときは、その項目の文をタイトルの初めの値にし（本文で文字を選んでいればそちらを優先）、行末の「（高橋）」のような担当者は担当者に入れます。作ると、その行の最後に ` → [ID](../tickets/ファイル名)` を付けます（AIの手順と同じ）。
  - 行は、項目の文（書式を除いた文字）で「宿題」の中から探します。同じ文の項目が複数あれば、まだ「→」の付いていない最初の項目にします。すでに「→」が付いている・作っている間に行が消えた、などで見つからないときは、「宿題」の最後に `- タイトル → [ID](…)` の行を足します。
  - 「宿題」の外で押したときも、「宿題」の最後に行を足します。「宿題」の見出しがなければ、「文字起こし」の前（なければ本文の最後）に見出しごと足します。付けたもののほかは1文字も変えません。ノートが外部で変わっていたときは、何も作らずに競合として知らせます。
- 「AI でタスクを起こす…」で、AI に議事メモからタスクの候補を出してもらえます。
  - AI は、パソコンに入っている Claude Code（`claude -p`）を呼びます。キーの管理は要りませんが、入っていないと使えません（見つからなければ案内を出す）。モデルは `sonnet`（その時点の最新の Sonnet）で、ファイルの読み書きなどの道具は使わせず、セッションも残しません。
  - 送る前に「このノートを AI に送ります」と確かめます。文字起こしには社外の人の発言や秘密の話が入ることがあるので、「文字起こしも送る」を外すと、要点・決定事項・宿題などだけを送ります。本文が長すぎる（12万字より多い）ときは途中までを送り、そのことを伝えます。
  - AI には RULES.md の「議事メモからタスクを起こす」の手順と、このノートからすでに作ったチケットのタイトルを渡し、手順の1（候補を出す）だけをしてもらいます。答えは決めた JSON の形（タイトル・担当者・期限・根拠の発言・宿題の行・迷い）で受け取ります。
  - 候補は一覧で出し、人が選んで直してから「作る」を押します（確認を挟む決まりはそのまま）。迷いのある候補は、初めは選ばないでおきます。作るのは「＋ ここからチケット」と同じ仕組みで、宿題の行から起こしたものはその行に、それ以外は「宿題」の最後に「→ リンク」を書き戻します。まとめて作るときは、作ったチケットを開かずにノートに留まります。
  - すでに作ったチケット（`source` がこのノートのもの）と同じタイトルの候補は外します。

### 9. 設定と起動時の処理

- 「設定」は、この PC だけの設定です（`tasks/` の外の `settings.json`）。自分の名前を入れると、新しいチケットの作成者・担当者に入り、担当者の絞り込みで「自分」を選べます。
- 設定の「ルールのファイル」で、`tasks/` の RULES.md・TEMPLATE.md・NOTE_TEMPLATE.md・CLAUDE.md・AGENTS.md がアプリの原本と同じかを確かめ、選んだものを原本にできます。違うファイルは、今のファイルを OS のごみ箱に移してから置き換えます（すでに使っているフォルダに新しいルールを届けるため）。`TAGS.md` は利用者のデータなので対象にしません。
- 初めての起動とバージョンアップのときは、「設定」ボタンに印（点）を付け、画面の上にひとこと案内の帯を出します。
  - 初めての起動では必ず「はじめに設定で自分の名前を入れてください」と出します。バージョンアップでは、ルールのファイルが原本と違うときだけ「ルールのファイルが新しくなりました。設定で更新できます」と出します。
  - 設定の画面を開くか帯を閉じると、今の版を個人設定（`settings.json` の `lastVersion`）に覚えて、次からは出しません。版を覚えていない古い設定でも、名前が入っていればバージョンアップとして扱います。
  - `tasks/` のフォルダを選ぶ前は出さず、選んだ後に出します。開発版とインストール版は設定が別なので、それぞれで出ます。
- 起動して `tasks/` を読み込んだ後（フォルダを選び直したときも）、ID だけのファイル名に見出しを付け足し、「◯件のファイル名に見出しを付けました」と案内します（条件は「ファイル名」の節）。

## 色の意味

1つの見せ方（塗り・丸・枠・線）には、1つの意味だけを持たせます。一覧・カレンダー・ガントチャートで同じ決まりを使います。

| 見せ方 | 意味 | 色 |
| --- | --- | --- |
| 予定・棒の塗り方 | 状態 | 未着手＝青の枠だけ（中は塗らない）、作業中＝濃い青の塗り、待ち＝淡い青の斜線、完了＝薄い灰色＋取り消し線 |
| 小さな丸 | 優先度 | 高＝赤、中＝黄、低＝灰 |
| 赤い枠と「!」の印 | 期限切れ | 赤。塗りは状態のままにする |
| 左の線 | タグ | 色相だけを選べる。鮮やかさと明るさはアプリが一定にし、パステル調にする |
| 選択中の枠 | 選んでいるチケット | 文字の色の太い枠（青い予定の上でも見えるよう、青を使わない） |

- **状態はカレンダーとガントチャートで同じ**にします。ガントの棒も状態の塗り方にします。まとめ棒（子のある親）は親自身の状態で塗り、両端を下に尖らせた形で普通の棒と見分けます。
- **赤は「急ぐ・注意」**です。優先度の高・期限切れ・警告と削除に使います。同じ「すぐ見てほしい」という意味なので、まとめています。
- **未着手と完了は、色ではなく塗り方で見分けます**（枠だけか、薄い灰色の塗りか）。低と完了はどちらも灰色ですが、低は小さな丸、完了は棒全体なので形で見分けられます。
- **色だけに頼りません**。期限切れには「!」の印を、完了には取り消し線を付けます。
- カレンダーとガントチャートの上の「?」を押すと、凡例を出します。普段は出しません。
- 色は `main.css` の変数（状態＝`--status-*`、優先度＝`--priority-*`、注意＝`--danger`）にまとめ、ダークモードの値も決めてあります。

見送った案：塗りを優先度にする（完了のグレーアウトとぶつかる）、ガントの状態を信号機の色にする（優先度の丸と意味がぶつかり、数の多い未着手が赤になって画面が警告だらけに見える）、状態に緑・紫を使う（色味がしっくりこない）。

## エディタ設計

本文の編集には、WYSIWYG型のエディタMilkdownを使います。WYSIWYG型は、保存するとmdが勝手に整形されることがあります。そのため、次の対策を組み込みます。

1. **frontmatterはエディタに渡さない**：ファイルを開いたらfrontmatterと本文を分け、本文だけをMilkdownに渡します。frontmatterはプロパティフォームで編集し、変わった行だけを書き換えます。
2. **編集していなければ保存しない**：開いて眺めただけのファイルには書き込みません。保存時も、変換結果が元の文章と実質同じなら、元のテキストのまま残します。
3. **エディタの書き方を正式な書き方にする**：書き出しの設定（remark-stringify）を「書き方のルール」の表と同じに固定します。人もAIもエディタも同じ書き方になるので、整形しても差分が出ません。
4. **変換を往復させるテストを用意する**：サンプルのmdを読み込んで書き出し、元と一致するかを確かめるテストを最初に作ります。エディタの設定やバージョンを変えたときに、すぐ異常に気づけます。
5. **編集していないブロックは元のテキストに戻す**：書き出しの設定を揃えても、`[` の前に `\` が付く、裸のURLが `<URL>` になる、などの違いは残ります。そこで保存するときに、本文を段落・見出し・リスト・表などのブロックに分け、編集していないブロックは元のファイルのテキストをそのまま使います。ただし、エディタが読み込むときにブロックの数や中身を変えてしまう本文（リンク参照定義があるなど）では、ブロックの対応が取れません。その場合は、開いたときに「編集すると本文全体が書き出し直される」と案内を出します。

あわせて、日本語入力（IMEの変換や確定）の動きは自動テストでは確かめられないので、エディタ周りを変えたら実際に入力して確かめます。
